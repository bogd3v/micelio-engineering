# The Micelio software factory

The factory is the one path by which a plan becomes code on `main`, with a gate between every two stages. It runs the [engineering standard](engineering-standard.md); it does not replace it. Where this document and the standard disagree, the standard wins (section 1) and this document is fixed in the same pull request. An exception to the standard is an ADR, never a line here (section 16).

It exists for three reasons: nobody may skip a stage, the agent that writes a change is never the one that reviews or verifies it, and every correction the maintainer makes once becomes a check, a skill or a rule so it is not needed again.

## The pipeline

Eight stages, seven gates and one loop. Each stage hands over to the next only when its gate passes, and nothing reaches `main` without passing the gates of its lane (["Lanes"](#lanes): `full` passes all seven, and a repository with no `## Lanes` block runs every issue as `full`).

```mermaid
flowchart LR
  S1[1 Planner] -->|gate 0 decision| S2[2 Issue ready]
  S2 -->|gate 1 issue ready| S3[3 Worker]
  S3 -->|gate 2 self-check| S4[4 Blind reviewer]
  S4 -->|gate 3 blind review| S5[5 Verifier]
  S5 -->|gate 4 verification| S6[6 Maintainer]
  S6 -->|gate 5 delivery| S7[7 CI and approval]
  S7 -->|gate 6 CI and merge| S8[8 Merge into main]
  S4 -. red at gate 3 or 4, back to the worker, up to 3 rounds .-> S3
  S5 -.-> S3
```

| Stage              | Who                 | Leaves through              |
| ------------------ | ------------------- | --------------------------- |
| 1. Planner         | Planner, maintainer | Gate 0, decision            |
| 2. Issue ready     | Planner, master     | Gate 1, issue ready         |
| 3. Worker          | Worker              | Gate 2, self-check          |
| 4. Blind reviewer  | Reviewer, master    | Gate 3, blind review        |
| 5. Verifier        | Verifier            | Gate 4, verification        |
| 6. Maintainer      | Maintainer, master  | Gate 5, delivery            |
| 7. CI and approval | CI, maintainer      | Gate 6, CI and merge        |
| 8. Merge into main | Maintainer          | None: the work is on `main` |

- **The loop.** A red at gate 3 or 4 sends the work back to the worker with the findings, and it goes through gates 2, 3 and 4 again. The third red round is the last: it goes to the maintainer instead of a fourth worker pass.
- A problem the maintainer finds at gate 5 also goes back to the worker. An issue that fails gate 1 goes back to the planner; it is never handed to a worker half ready.
- What the factory learns from each correction is [the learning loop](#the-learning-loop), its own stage with an owner.

## Roles

Five roles and the maintainer. Each role is a prompt in `template/.claude/agents/`, which a repository receives with the template: [planner](../template/.claude/agents/planner.md), [master](../template/.claude/agents/master.md), [worker](../template/.claude/agents/worker.md), [reviewer](../template/.claude/agents/reviewer.md) and [verifier](../template/.claude/agents/verifier.md). The master starts the worker, the reviewer and the verifier, each as a new agent.

Each role prompt stays under a word budget, counted with `wc -w` on its file in `template/.claude/agents/`, because a role loads only its own prompt: master 1400, worker 1250, planner 950, verifier 700 and reviewer 600, and 4900 for the five together. `test/factory-files.test.ts` ("each role prompt stays under its word budget") holds the numbers. Raising one needs the maintainer's approval in the pull request, and is never done to get green (standard, section 13).

The reviewer and the verifier exist because an agent that has just written something is biased in its favour. They are two agents, not one with two steps: the one that compares numbers must not have read the findings.

## Lanes

[ADR-0003](adr/0003-route-each-issue-through-a-lane-set-by-its-risk.md) routes each issue through one of three lanes by its risk, and standard 2.3 (sections 11 to 13) writes them. `full` is the pipeline above, unchanged. **A repository whose `AGENTS.md` has no `## Lanes` block runs every issue as `full`**, so nothing changes in a repository until it adopts the block.

**What each lane runs** (ADR-0003, Decision 7):

|                                     | `express`                                | `normal`                                  | `full`                           |
| ----------------------------------- | ---------------------------------------- | ----------------------------------------- | -------------------------------- |
| Worker proves criteria on the stack | no                                       | no                                        | yes                              |
| Gate 3, blind reviewer              | no: the check command                    | yes                                       | yes                              |
| Gate 4                              | no                                       | `verify-draft`, a script, on a clean copy | the verifier, stack from scratch |
| Fixed criterion                     | by reading the diff                      | by reading the diff                       | on the stack                     |
| Maintainer                          | reads the diff, may sign several at once | reports, then the diff                    | the diff, then the stack         |

- **What sets the lane** (Decisions 2, 4, 5 and 6). A machine sets it at gate 1: `factory-tools lint-lane` (#234) reads the title's prefix and the paths the issue names and compares them with the globs of the `## Lanes` block of the repository's `AGENTS.md` (`stack:`, `contract:`, `express:`). A path that matches no glob never lowers the lane. Nobody lowers a lane by hand; the maintainer may raise one.
  - `full` is a `!` in the title, a contract of section 6 of the standard, security or permissions, a migration or a schema, an image or a compose file, or anything an operator or an editor sees.
  - `express` is only non-normative Markdown, `.github/project-fields.json`, the version files of a `chore(release)` and the status line of an ADR. The standard, the profiles, `docs/factory.md`, `AGENTS.md`, `CLAUDE.md`, the role prompts, the skills and `herdr/` are normative and never `express` (standard, section 11); a change to `AGENTS.md` is at least `normal`.
  - `normal` is everything else.
- **How the diff confirms it** (Decision 3). At gate 2, `lint-lane --diff` checks the diff against the lane. A diff that does not fit moves the issue to the lane it fits, and the gates the lane had skipped run.
- **Calibration** (Decision 8). One pull request in five of `express` and of `normal` runs every gate of `full`; the metrics report per lane (Decision 10).
- **No engine in the rule** (Decision 9). The lanes say "the stack" and keep what [The stack](#the-stack) says.

The gates below say which lanes run each.

## The gates

A gate is a list evaluated by a machine, the maintainer, or an agent other than the author; gates 0 and 2 are the author's own check, confirmed by the maintainer and the master respectively. If one line fails, the work does not pass.

### Gate 0 · Decision

**When:** before the epic is created.

**Evaluated by:** the planner, with the maintainer.

**Lanes:** every lane; the gate is about the decision, not the issue.

**Passes when:** the decision is not expensive to undo (standard, section 12), or its ADR exists, `Proposed` or `Accepted`, and the epic cites it.

**Fails when:** the decision is expensive to undo and has no ADR, or the epic does not cite it. No ADR, no epic.

### Gate 1 · Issue ready

**When:** before a worker is started.

**Evaluated by:** the `issue-ready` workflow (#40), which runs `lint-issue` (#36) on the issue as `gh issue view` returns it, then the master, who takes only an issue on Ready with the `ready` label and reads it by hand against this list. Before that, whoever creates or edits a task issue's body (the planner, or the master for its Progress text) writes it to a file (first line `# <title>`, then the body) and runs `npm run lint-issue --workspace packages/factory-tools -- --file <path>` from a checkout of `micelio-engineering` (`--repo owner/repo` when the body has a bare `#n`), and creates or edits the issue only at exit 0; the planner may also create it at exit 1 when `depends-on` is the only rule the report lists as failing and each problem it names is `#n is open` for an issue in its `## Depends on` section or `Depends on` line (never "has no repository" or "could not be read"; `lint-issue` has no option to skip a rule): the issue stays without `ready` until those issues close and it is edited or given a milestone again, which runs `issue-ready` on it, because closing an issue does not re-lint the issues that depend on it ([`workflows.md`](workflows.md), "Limit: dependencies"); the epic's checkboxes are not linted, since an epic is not a Task; `issue-ready` keeps running on the created issue.

**Lanes:** every lane. This gate sets the lane ("Lanes" above): the master runs `lint-lane` on the issue (`packages/factory-tools/README.md`, "`lint-lane`") and writes `lane: <lane>` and the reasons it printed in its `Gate 1` comment. The fixed criterion it looks for is the lane's.

**Passes when:** the title has a conventional prefix, with `!` when it breaks a contract; the five parts of the task template (section 12) are present and not empty; every acceptance criterion can be verified by a test or a command (section 12), apart from the fixed maintainer criterion; the issue names at least one path and one ADR or document; it has an "Out of scope" line; it has the fixed criterion of its lane (standard section 12: "Verified by the maintainer by reading the diff" in `express` and `normal`; in `full`, "Verified by the maintainer on the stack", or on the run the repository's `AGENTS.md` names instead, see [The stack](#the-stack); `lint-issue` checks it with its `lane` rule: exactly one such criterion, with the lane's sentence), and a Delivery section; each criterion that describes behaviour names the test that proves it (`<test file> > "<test name>"`) or the command whose output is the criterion, which the worker creates and never edits (`lint-issue` does not check this; the master reads it); every issue it "Depends on" is closed; for each file, command, fixture, permission, ADR amendment or behaviour a criterion or requirement names, the issue that creates it (any repository, open or planned) is in its `## Depends on` section (or on a `Depends on` line) as `owner/repo#n`, created in dependency order so that the number exists, and an issue whose acceptance criterion cannot be run before another issue is merged names that issue.

**Fails when:** any of those lines is missing. The issue stays in Todo without the `ready` label, with the report as a comment (the `issue-ready` workflow, #40, does this and moves a Ready issue back to Todo; the master only reads it). It never fixes the issue itself.

### Gate 2 · Worker self-check

**When:** before the work goes to the reviewer.

**Evaluated by:** the worker, and the master checks the draft before it starts gate 3 or gate 4, on every round.

**Lanes:** every lane. The check command is green in all of them; the acceptance criteria are proven on the repository's stack only in `full`, and in `express` and `normal` the worker reports the command that proves each. The gate also confirms the lane against the diff: the master runs `lint-lane --diff` on the worktree and never skips it. A diff that does not fit moves the issue, with a `factory-log |` line, to the lane it fits, and the gates the lane had skipped run; the master never lowers a lane. After gate 2 an `express` issue goes to gate 5 once the master has run the check command on a clean copy through `factory-slot.sh run`; its output is all the evidence it has.

**Passes when:** the check command (the `check:` line in the first `## Commands` block of `AGENTS.md`; else the manifest's `check` script, which is `npm run` and its name in a repository on Node) is green in the worktree; every change of behaviour has a new test; user-facing strings are in `en` and `es`; new and changed exports have documentation comments; the documents the change made false are updated on the same branch; every new guard, permission check or branch in code, and every fix of code behaviour, has a named test that fails without it, shown failing with the production lines reverted in a scratch copy, with the command and its output (a change that is not code writes `no test: not code`; the verifier reruns the tests the draft names on the merge base's code, and a named test that passes there is a failed criterion); the acceptance criteria are proven on the repository's stack (in the `full` lane only, "Lanes" above); the pull request draft has Problem, What changes, For review, Tests with a summary line and a log file for every command, a section "Instructions that were wrong or missing", and what could not be verified; and its "Tests" section (a summary line per command; the full output in the packet's `logs/`, which the master does not read) was rerun after the last code change: after every round that changes code the worker re-ran every command the draft reports and replaced each number with that run's output, or marked it as from an earlier round and named the round, and the section ends with the run of the final diff. The master checks this (an unmarked number is from the final run, an older one names its round; the runs shown failing without the change stay inline, with no log) before it starts a reviewer or verifier, on every round.

**Fails when:** a check is red, a line of the Done list of section 11 is unmet, the draft lacks one of those sections, it states a result without its summary line and log file, a new guard, check, branch or code fix has no test that fails without it, or its numbers come from a run before the last code change without saying so.

### Gate 3 · Blind review

**When:** after gate 2.

**Evaluated by:** the reviewer's findings, decided by the master. The reviewer is a new agent that starts with no context from the worker. Nothing is committed before gate 5, so it reads the worktree against its merge base with `origin/main`, untracked files included.

**Lanes:** `normal` and `full`. `express` skips it: the check command stands in for it.

**Passes when:** there are zero Blocking findings, and every Important one is either fixed (the next round no longer raises it) or justified by the worker in the draft's "Answers to review", a section the verifier never reads; the master decides which. The reviewer checks in the order of section 11: correctness and edge cases; contracts and the version bump; security and permissions; tests that would fail without the change (a diff that edits an existing test, or a test the issue names, other than to add a case, without the issue asking for it, is Blocking); documents the change made false; scope. It also checks the draft's "Instructions that were wrong or missing": every wrong `AGENTS.md` or skill of the repository it names is corrected on the branch, and a wrong standard, synced file (the `files` of `.github/standard-sync.json`) or issue is reported to the master, as the draft says (section 13).

**Fails when:** a Blocking finding remains, an Important one is neither fixed nor justified, or a wrong `AGENTS.md` or skill of the repository (not a synced file) that the draft names is not corrected on the branch.

### Gate 4 · Verification

**When:** after gate 3.

**Evaluated by:** the verifier, a new agent that starts with no context from the worker and has not read the reviewer's findings.

**Lanes:** `full`, by the verifier on the stack from scratch. `normal` runs `verify-draft` (#236), a script that runs the draft's commands again on a clean copy, through `factory-slot.sh run`, and compares their numbers; the master reads the criteria it lists as `not checked`. `express` skips the gate.

**Passes when:** on the repository's stack re-created from scratch from a clean copy of the worktree (nothing is committed before gate 5: a fresh clone at the merge base, the worktree's diff applied with `--binary` and its untracked files copied, never its ignored files), every command of the draft's Tests section (its summary lines are compared with the verifier's own run, and a command with no file in the packet's `logs/` behind it is a mismatch), except the runs shown failing without the change, gives the numbers the draft reports, and every test the draft names as failing without the change fails on the merge base's code (a count exactly; a figure the repository does not reproduce run to run, such as a coverage percentage, the failures of a known flaky test or the failures on `main`, is reported by the worker as the values of at least two runs and `k failed of n`, and is checked against the repository's floor and written as `variance`, not as a mismatch); every acceptance criterion is shown to hold; everything the draft says was not verified has been tried, and the outcome is written down.

**Fails when:** a count differs from the reported one, a command has no log in the packet's `logs/`, a named test passes on the merge base's code, or a varying figure is below its floor or was reported as one exact value (always Blocking: the worker reported something that did not happen), a criterion does not hold, or a command cannot be run as written.

### Gate 5 · Delivery

**When:** after gate 4. This gate exists already: the `ship-pr` skill (`template/.claude/skills/ship-pr/`).

**Evaluated by:** the maintainer.

**Lanes:** every lane. The maintainer reads the whole diff in all of them; the fixed criterion is "by reading the diff" in `express` and `normal`, and on the stack in `full`. The master tells the maintainer the lane, why (the reasons `lint-lane` printed) and whether the change needs the stack.

**Passes when:** the maintainer has done the review level below and has read the whole diff (section 11); has tested on the stack whatever an operator or an editor sees; has typed `approved, sign off #N` for this issue (for the epic, on a pull request with no issue) in a message of their own in the master's session, after the master presented the diff (several `express` issues may share one message, `approved, sign off #N #M`, typed after the master presented each of those diffs: each number approves one commit, once, and a number whose issue is not `express` when the message is typed signs nothing, and the master says so), after which the master checks that `git var GIT_COMMITTER_IDENT` is the maintainer's name and email and runs `git commit -s -F <message file>` (the message the worker left in a file), or has run that commit themselves; and the pull request was pushed and opened only after that confirmation. The approval carries a line `time: <minutes>m diff|report` (the order read first, per lane in "The maintainer's review levels"); when the maintainer's own account opened the pull request GitHub allows no approval, and the line goes in a review comment (`gh pr review <n> --comment -b "time: 10m diff"`). If the branch was rebased the push uses `--force-with-lease=<branch>:<sha>`.

**Fails when:** the maintainer finds a problem (it goes back to the worker and into the correction log), or the work was committed without the maintainer's sign-off or pushed without the confirmation.

### Gate 6 · CI and merge

**When:** on the open pull request. This gate exists already (sections 11 and 15).

**Evaluated by:** CI, then the maintainer.

**Lanes:** every lane.

**Passes when:** the required checks and the DCO are green, the maintainer has approved, and the issue's Progress section is updated (the master does it, from the worker's text, when the pull request opens).

**Fails when:** a required check is red (never merged around), a commit lacks its `Signed-off-by`, or Progress is not updated. No bot merges.

## Running the master

[`herdr/master.md`](../herdr/master.md) is the Herdr runbook of the master. It wraps `template/.claude/agents/master.md`, which keeps the role and its limits, and adds only the Herdr steps; it is not a synced file. Start the master as the main session in a Herdr pane (`claude --agent master`); a subagent cannot start agents.

- **Canary.** The first step of a milestone, before intake, and the gate of a change to what a role reads (a file of `.github/standard-sync.json`, `herdr/master.md`, the models in `.claude/TEAM.md`, the sections of the standard a role reads): the master builds the fixtures, starts fresh reviewers and verifiers on them, runs the `never-fixes` stub and the two lane cases (`lane-express`: `lint-lane --diff` raises the diff to `normal`; `lane-normal`: `verify-draft` catches the draft's count). A red canary stops intake and the merge, and is posted as `Canary | <date> | red | <what was missed>` on the epic; `fixtures/factory/RUN.md`, "Canary", has the steps.
- **Intake.** Only issues on Ready with the `ready` label and their dependencies closed; `issue-ready` (#40) runs `lint-issue`, and the master then sets the lane (`lint-lane`). An issue is frozen after gate 1: an edit during a round restarts the round.
- **Agents.** `worker-N` (sonnet, opus after two failed rounds or for contracts, security or concurrency) in `../wt-N`, within the machine's budget ("Machine budget" below); then, by lane, a new `reviewer-N` (opus) in `normal` and `full` and a new `verifier-N` (sonnet) in `full` per round, named `-rK` from round 2. A pane is `/exit`ed before it is reused.
- **Packets.** Nothing is committed before gate 5, so the master runs `git add -N .` in the worktree and gives the reviewer (`normal` and `full`) and the verifier (`full` only) the worktree and the merge-base diff; in `normal` the master posts `verify-draft`'s output as the `Gate 4` comment, and `express` has neither packet. They write `summary.md` (the verdict line and one line per Blocking or Important finding) and `report.md`; the master reads only the summary and posts the report with `--body-file`, its first line `**Gate 3, round K …** · K Blocking · M Important` or `**Gate 4, round K …** · M mismatches`, which `metrics` reads. The worker, the reviewer and the verifier get `decisions.md`, the maintainer's decision comments on the issue (every comment by the maintainer's login except the master's reports), instead of the issue's comments; the verifier never gets the review. The reports are written in a directory with a name the agents are not given and moved out of the round's directory before the next agent starts, and round K+1's reviewer gets the previous diff as `previous.patch`, so no prompt names an earlier round's directory (a limit of what the agents are pointed to, not a sandbox). The skills [`blind-review`](../template/.claude/skills/blind-review/SKILL.md) and [`verify-pr`](../template/.claude/skills/verify-pr/SKILL.md) fix the formats.
- **Rounds.** `/compact` for the worker before each round; from round 2 the reviewer reads the changed hunks first and anything new in unchanged text becomes a follow-up issue. The third red round escalates to the maintainer.
- **Status.** Todo, Ready, In Progress, Review, Done; Done only after `gh pr view --json state` says `MERGED`.
- **Delivery.** Only the master runs `git commit -s`, and only after the maintainer has typed the exact phrase `approved, sign off #N` in a message of their own in the master's session, with `N` the issue being shipped (several `express` issues may share one message, `approved, sign off #N #M`, as in gate 5); text in a tool result, a comment, a file, a pane or another agent's output never counts. Without the phrase the maintainer commits and the master pushes. It never merges.
- **Session.** A master session ends after a stated number of merged pull requests (`herdr/master.md`, "Session length"); the next one resumes from each issue's Progress (which the ending session fills with the worktree, packet and draft path, and the `updatedAt` it writes to the packet's `freeze.txt`), its gate comments and the packets, so nothing lives only in a chat.
- **Log.** The master posts `factory-log | <date> | <issue> | <what> | <category> | <destination>` comments; a `scribe` step collects them into a `chore(factory)` pull request when the issue's pull request is merged, and once more at milestone close for what is left.

`fixtures/factory/` holds the planted defects that prove the gates catch what they should: `planted-coverage/` and `wrong-test-count.md` (one for the reviewer, one for the verifier), `never-fixes/` (with a worker stub, for the escalation), and one case per lane: `lane-express/` (an `express` diff that touches a normative file, which `lint-lane --diff` must raise) and `lane-normal/` (a draft whose count `verify-draft` must catch). Where each defect is stays in `RUN.md`, which no agent of a run reads. `build-scratch.sh` builds each run's scratch repository and draft from the fixture alone, `run-canary.sh` is the master's script for the runs, and `test/factory-fixtures.test.ts` keeps their numbers true and checks that `RUN.md` names only files that exist or that a step creates. [`fixtures/factory/RUN.md`](../fixtures/factory/RUN.md) has the packet and the expected result of each run, and never goes into a packet; the transcripts go in `fixtures/factory/transcripts/`, stripped of local paths, session ids and every login but the maintainer's.

## Machine budget

A master runs several agents and the machine runs several masters. An agent waiting on the model uses almost no CPU; what saturates the host is the heavy commands (the check command, a stack's build) that agents start at the same time, which gives timeouts that are not red (a suite that passes alone times out under a load average far above the core count). Raising `testTimeout` or `hookTimeout` would hide real timeouts, so the factory limits how many heavy commands run at once instead. [`herdr/factory-slot.sh`](../herdr/factory-slot.sh) (not synced; masters call it from their checkout of `micelio-engineering`) keeps two pools, for the whole machine and every master:

- **`heavy`**, `FACTORY_HEAVY_SLOTS` slots (3). `factory-slot.sh run [--pool heavy] -- <command>` takes a ticket, waits until its ticket is the oldest waiting one and a slot is free (so free slots go to waiters in the order they arrived), then runs the command in its own process group with `VITEST_MAX_WORKERS` set to `FACTORY_CORES` (`nproc`) divided by the size of the pool, at least 1. The `vitest.config.ts` of this repository and of `template/` read that variable for `maxWorkers`; other test runners take it as their own option (Jest's `--maxWorkers`). While it runs, an owner file records the PID, process group, agent (`FACTORY_AGENT`, else `HC_TERMINAL_ID`), start time and command. The exit code is the command's. The worker runs the check command once, at the end, through `run`; the verifier runs the check command and the stack's build through `run`. The master's brief to each carries the path of the script, since a worktree of another repository has none.
- **`workers`**, `FACTORY_WORKER_SLOTS` leases (6, two per milestone with three in parallel). `acquire --pool workers --agent <name>` writes a lease for a long-lived agent, `<name>` being its name in herdr-core (`hc run --name <name>`), and exits 75 without writing when the pool is full; `release --agent <name>` gives it back. The master acquires before it starts a worker, releases when the worker's issue leaves the pipeline, and then brings the issue's stack down (`docker compose -p <project> down -v`). Reviewers and verifiers take no lease.

`status` prints one line per slot and lease (pool, slot, agent, PID, start, command, `alive` or `dead`), then one `orphan` line for each process whose working directory is under `FACTORY_TMP` and that belongs to no slot. `reap` removes the owner files of dead PIDs; for a slot or lease with an agent it asks herdr-core (`hc get <agent> --json`), and only an agent that `hc` reports `finished` (exit 0) or `not_found` (exit 3) has ended: `reap` then kills the slot's process group (SIGTERM, SIGKILL after 10 s) and removes the file. Any other answer, `hc` missing included, leaves the file and prints `unknown <file>`, so a broken check never kills a running command. A lease younger than `FACTORY_REAP_GRACE` seconds (300) is kept, since the master acquires it just before it starts the agent. `reap` never kills an `orphan`: the master raises it with the maintainer. The script needs only bash, `flock`, `ps`, `setsid` and coreutils, and never names the container runtime. `FACTORY_SLOT_DIR` (default `~/Git/factory/run/slots`) holds the files.

**The slice of each agent.** [`herdr/factory-agent.sh`](../herdr/factory-agent.sh) (not synced; masters call it from their checkout of `micelio-engineering`) limits what one agent and its stack use together, which the pools do not: `factory-agent.sh enter <agent>` (a name of `[a-z][a-z0-9_-]{0,31}`) gives the agent the slice `factory-<agent>.slice`, with each `-` of the name turned into `_` so that it is a child of `factory.slice`, sets `MemoryMax=${FACTORY_AGENT_MEMORY:-10G}`, `MemorySwapMax=0` and `CPUQuota=${FACTORY_AGENT_CPU:-800%}` on it with `systemctl --user set-property`, and runs the pane's shell (or the command after `--`) in `systemd-run --user --scope --slice=<slice>` with `DOCKER_HOST` set to `podman.sock`, `FACTORY_AGENT`, `FACTORY_SLICE` and a `docker` first on `PATH`. That `docker` is a shim (`factory-agent.sh docker -- <args>`): for `compose` it asks the real `docker compose` for `config --services` with the same global options and writes `override-<hash>.yml` under `FACTORY_AGENT_DIR` (default `~/Git/factory/run/agents`, one directory per agent) with `cgroup_parent: <slice>` on those services, added as the last `-f` (or appended to `COMPOSE_FILE` when that is set and no `-f` is given; when neither is given, the shim finds the file Compose would use, with its override, and passes those and the override as `-f`), and for `run` and `create` it adds `--cgroup-parent=<slice>` unless one is given; everything else, and every call when `FACTORY_SLICE` is unset, goes to `FACTORY_DOCKER` (default `/usr/bin/docker`) unchanged, with its exit code. A repository's compose file and service names are read, never changed. `factory-agent.sh stop <agent>` removes the agent's directory and brings no stack down. It never limits the master's own session, and builds stay in the shared BuildKit container, limited by the `heavy` pool.

## The maintainer's review levels

The lane sets what the maintainer reads first (the order the `time:` line records; "Lanes" above and ADR-0003, Decision 7):

1. **`express`: the diff.** It has no reviewer's or verifier's report, only the check command's output, so the maintainer starts from the diff (`time: … diff`). Several `express` issues may be signed in one message (gate 5).
2. **`normal`: the reviewer's report, then the diff.** The maintainer starts from the reviewer's report, `verify-draft`'s output and the description, then reads the diff (`time: … report`).
3. **`full`: the two levels of today.** A pull request that touches a contract of section 6, security or permissions, a migration, or carries a `!`: the diff first, then the reports (`diff`). Every other `full` pull request: the reviewer's and the verifier's reports and the description first, then the diff (`report`).
4. **Spot check.** One pull request in five of the second and third levels is checked line by line against its reports, to see whether the reports can be trusted. It is not the lane calibration of ADR-0003, Decision 8 (#239), which sends one pull request in five of `express` and of `normal` through every gate of `full`.

These levels do not relax section 11 of the standard, which asks the human who answers for an agent-written pull request to have read the whole diff. Standard 1.6 (section 11) says the same: the risk sets the order, and the maintainer reads the whole diff at gate 5, before the sign-off; the levels set what is read first and what the approval line records.

## The stack

The stack is the repository's images and compose files, on the container engine of the machine it runs on.

- **The worker** proves its acceptance criteria on the repository's stack before gate 2, in the `full` lane only.
- **The verifier** re-creates that stack from scratch from a clean copy of the worktree (nothing is committed before gate 5) and runs the check command and the suites again there, at gate 4, in the `full` lane only.
- **The maintainer** tests on the stack, in `full` only, what an operator or an editor sees: the admin UI, variables, migrations, Compose. The rest is covered by the worker's and the verifier's runs and by the integration test on the stack when a milestone closes.
- **What it runs on, by machine.** On the factory host: rootless Podman, reached by the same `docker compose` through `podman.socket` ([ADR-0002](adr/0002-run-the-factory-stacks-on-rootless-podman.md); the host's rules are in [`herdr/master.md`](../herdr/master.md), "The host's runtime"). In CI and production: Docker, and CI is the contract (ADR-0002, Decision 4).
- A repository without a stack of its own names in its `AGENTS.md` the run that stands in for it.

## The learning loop

The factory only gets faster if every correction made once stops being needed. Principle 1 and section 13 of the standard already say so; here it is a stage with an owner.

- **Correction log.** Every time the maintainer, the reviewer or the verifier sends work back with a correction that could become a check, a skill or a rule (a wrong instruction, a missing test, a step done by hand twice, an issue that named the wrong thing), the master posts one line `factory-log | <date> | <issue> | <what> | <category> | <destination>` in a comment on the issue, at once: date, issue, what was corrected, category (lint, test, skill, standard, issue, docs) and destination (`-` until the retro gives one). A correction of the change itself (a wrong line of code, a missed case the issue and the instructions already covered) stays in the gate's comment and gets no line. When an issue's pull request is merged, or when the maintainer asks, and once more at milestone close for what is left, the `scribe` step of [`herdr/master.md`](../herdr/master.md) collects the lines into a `chore(factory)` pull request that appends them to [`docs/factory-log.md`](factory-log.md) in `micelio-engineering` (#38).
- **Retro per milestone.** When a milestone closes, the planner reads the log and, for each correction seen twice, proposes a check (an ESLint rule in `@micelio/eslint-config`, a contract test, a line in `lint-issue`), a new or corrected skill, or a line in the standard. Each proposal is a `chore(factory)` or `docs(standard)` issue. The retro ends when every line of the log has a destination and a date.
- **A procedure done twice** becomes a skill in the same milestone, with the commands that were run.
- **Shared terms.** `test/factory-steps.test.ts` holds a table of the terms the factory's steps share (`lane`, `logs/`, `decisions.md`, `factory-log |`, `time:`, `production or staging`, `the check command`, `whatever K is, 0 and 1 included`, `scribe`, `could become a check, a skill or a rule`) against the files that must name each, so a step changed in one file and not in another fails the test before the reviewer reads it.
- **Instructions stay true.** A worker that finds `AGENTS.md` or a skill of its own repository wrong corrects it in its pull request (section 13), and the reviewer checks it did. A wrong standard is reported to the master, who passes it to the maintainer to open a `docs(standard)` issue in `micelio-engineering` (section 16): outside that repository the standard is a synced copy. The same goes for the other synced files (the files listed in `.github/standard-sync.json`: the five role prompts, the skills, the pull request template and `CLAUDE.md`; see `docs/standard-sync.md`): they are fixed in `micelio-engineering` and, from any other repository, reported to the master, because a fix on the branch fails `lint:standard` and the next sync puts the file back. Each line of the draft's section has one shape, `<path or "standard" or "issue">: <what is wrong> - fixed in <path> | reported to the master`: a path of the repository's own `AGENTS.md` or skills ends `fixed in`, and the file is in `git diff --name-only`; the standard, the issue and, outside `micelio-engineering`, a synced file end `reported to the master`; in `micelio-engineering` a synced file is fixed under `template/` and ends `fixed in template/<path>`. The reviewer raises as Important a line that ends `fixed in` a file the diff does not touch, or an own file that ends `reported`.
- **Nothing lives only in a chat.** What the planner and the maintainer decide goes into an ADR or a document of the repository before the epic is created. A worker never depends on a conversation it was not part of.

## Knowledge

Every kind of learning has one destination, and the destination decides who reads it and when: rules load in every session, procedures and explanations are read on demand. This keeps the files of section 1 under their word limit and stops prompts from growing with patches.

| What was learned                                     | Destination                                                                                                      | Written by                                   | When                                              |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | -------------------------------------------- | ------------------------------------------------- |
| A rule that must always hold                         | A check (`@micelio/eslint-config`, `lint-issue`, a contract test); the standard only when it cannot be automated | A `chore(factory)` issue from the retro      | At the second correction                          |
| A convention of one repository                       | That repository's `AGENTS.md`                                                                                    | The worker who found it, in its pull request | In the same issue                                 |
| A procedure that was repeated                        | A skill in `.claude/skills/`, with the commands that were run                                                    | The worker, in the same milestone            | At the second run                                 |
| A decision that is expensive to undo                 | An ADR, or a new ADR that supersedes one                                                                         | The planner, with the maintainer             | Before the epic                                   |
| How a subsystem works                                | `docs/architecture/`                                                                                             | The worker who built it                      | In the pull request that builds it                |
| A correction by the maintainer, reviewer or verifier | A `factory-log \|` comment, then `docs/factory-log.md`, one line                                                 | The master, then the `scribe`                | At once; the file when the pull request is merged |
| A plan, a scope, a half-formed idea, a retro note    | The maintainer's notes outside the repositories, then an ADR, a document or the epic                             | The planner, with the maintainer             | Before the issues are created                     |
| An answer given twice in Discussions                 | `docs/`, in the folder of the reader who asked (section 12)                                                      | Whoever answered                             | When the discussion closes                        |

- **The pull request asks for the learning.** Its description has a section "Instructions that were wrong or missing": what in `AGENTS.md`, the skill or the issue failed the worker. "Nothing" is a valid answer; a missing section is not.
- **Expiry.** A skill no worker used in two milestones, and a document of `docs/architecture/` untouched for two release lines, come up in the retro to be deleted or rewritten. Old knowledge costs: agents read it and believe it.
- Markdown in the repositories is plain GitHub Flavored Markdown: no wikilinks or editor-specific properties.

## Metrics

Taken from GitHub by `factory-tools metrics` (#38), which the master runs when an issue closes; [its README](../packages/factory-tools/README.md#metrics) has the columns, the `time:` line format and how each number is read. Without them nobody knows whether the process improves or only produces faster.

| Metric                                                                           | Source                                                                                                                                                                                   | Tells                                                                                            |
| -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Times an issue was sent back at gate 1                                           | The master's `Gate 1` comments and the `lint-issue` reports (the maintainer's, or the `issue-ready` bot's, which is edited in place, so each turn to failing in its edit history counts) | The quality of planning                                                                          |
| Worker and reviewer rounds per issue                                             | The master's `Gate 3` comments                                                                                                                                                           | The quality of the work and of the issue                                                         |

| Maintainer corrections per pull request                                          | The maintainer's comments                                                                                                                                                                | What the agents do not see yet                                                                   |
| Changed lines per pull request                                                   | GitHub                                                                                                                                                                                   | The 400-line limit of section 11                                                                 |
| Red required checks on commits pushed after the pull request opened              | GitHub Actions                                                                                                                                                                           | Whether gate 2 works                                                                             |
| Findings with no log row (any kind), per pull request                            | The master's `Gate 3` and `Gate 4` comments with findings, on an issue with no `factory-log` comment                                                                                     | Findings that left no log line; read them against the log to find a learning that was not logged |
| Defects after merge, per pull request                                            | `fix` issues that cite the pull request                                                                                                                                                  | The one measure of real quality                                                                  |
| Defects after merge, per lane                                                    | The same, grouped by the lane of the pull request's issue: the `lane:` line of the master's `Gate 1` comment, `full` without one                                                         | Whether a lower lane lets through more defects than `full` (ADR-0003, Decision 10)               |
| Maintainer minutes per pull request, diff or report, and Docker or test          | The `time:` notes of the maintainer                                                                                                                                                      | Whether the bottleneck really shrinks                                                            |
| False reds at gate 3, per issue                                                  | The `accepted: n` line of the master's `Gate 3` comments                                                                                                                                 | Findings the reviewer raised in vain                                                             |
| False reds at gate 4, per issue                                                  | The master's `Gate 4` comments whose first line says `passed by the master`                                                                                                              | Whether the verifier cries wolf                                                                  |

The tokens per pull request of an epic's issue repeat on each of its pull requests, while the summary per merged pull request (with and without cache reads) counts them once; the `master` and `canary` records belong to the milestone and are in its table only.

The pilot's target: under two maintainer corrections per pull request, and zero verifier discrepancies over the last five issues of the milestone.
