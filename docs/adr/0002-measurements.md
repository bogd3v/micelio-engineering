# Measurements for ADR-0002: Docker and rootless Podman on the factory host

Evidence for [ADR-0002](0002-run-the-factory-stacks-on-rootless-podman.md). Taken on 2026-11-11 on the factory host by an agent the maintainer started there, one runtime after the other, with no other agent working and no other stack up (`hc ls`, `docker ps` and `podman ps` checked before each run; the output is in `logs/*.preflight.log`). The full output of every command and the scripts are kept in the packet of issue #196, outside the repository and not published; this file holds the numbers and how they were taken.

## Method

- **Podman through the Docker CLI.** Every Podman run is the same `docker compose` binary pointed at the user's socket: `DOCKER_HOST=unix://$XDG_RUNTIME_DIR/podman/podman.sock docker compose -p <project> ...`. Docker runs use the same command without `DOCKER_HOST`.
- **A clean copy per run**: `git clone --no-hardlinks` of the repository at `1d8f43c`, `git init && git add -A`, `.env` from `.env.example` with the keys of `npm run generate:keys`, a random `DATABASE_PASSWORD`, `URL`, `FRONTEND_URL` and no `PORT` (never printed). Ports `1347`; one project name per run (`e196-<runtime>-<n>`).
- **Two runs per runtime**, in this order: Docker 1, Docker 2, Podman 1, Podman 2 for measurements 2 and 3; then Docker 1, Docker 2, Podman 1, Podman 2 for measurement 1. The base images (`node:22-alpine@sha256:fe4f6d74…`, `postgres:18-alpine`, `node:22`) were pulled on both runtimes before the first run and are not timed; the build ran with `--no-cache`, so the first-level layers and the npm cache mounts were cold on both.
- **Counts are exact; times, load and memory are not reproducible**, so each is reported as its values and the number of runs (`k of n`). Two runs show the spread, not a bound; the verifier's variance rule applies.

### 4. The limit

Command: `systemd-run --user --scope -p CPUQuota=800% -p MemoryMax=10G <script>`; the script starts the stack and reads `/proc/<pid>/cgroup` of each container's main process. The scope's own `memory.max` read `10737418240` and `cpu.max` `800000 100000`.

| Variant (all from inside the scope)                                                                                                                                                                 | Where the containers' cgroups are                                                                    | Under the scope?                         |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| `docker compose up` (Docker daemon)                                                                                                                                                                 | `/system.slice/docker-<id>.scope`                                                                    | No                                       |
| `docker compose up` with `DOCKER_HOST` at `podman.sock`                                                                                                                                             | `/user.slice/user-1000.slice/user@1000.service/user.slice/libpod-<id>.scope/container`               | No: the user's instance, not the scope   |
| `podman run` (CLI)                                                                                                                                                                                  | the same `user@1000.service/user.slice/libpod-<id>.scope/container`                                  | No                                       |
| `podman run --cgroup-parent=<the scope's path>`                                                                                                                                                     | `Error: did not receive systemd slice as cgroup parent when using systemd to manage cgroups`         | Refused                                  |
| `podman --cgroup-manager=cgroupfs run --cgroup-parent=<the scope's path>` (the scope started with `Delegate=yes`)                                                                                   | `.../app.slice/run-<id>.scope/libpod-<id>`                                                           | Yes                                      |
| `docker run --cgroup-parent=<the scope's path>` (Docker daemon)                                                                                                                                     | `cgroup-parent for systemd cgroup should be a valid slice named as "xxx.slice"`                      | Refused                                  |
| `docker run --cgroup-parent=user.slice` (Docker daemon)                                                                                                                                             | `/user.slice/docker-<id>.scope`: the system manager's `user.slice`, outside `user@1000.service`      | No                                       |
| `docker compose up` with `DOCKER_HOST` at `podman.sock` and `cgroup_parent: e196-agent.slice` on both services (a compose override file outside the repository), the shell in a scope of that slice | `.../user@1000.service/e196.slice/e196-agent.slice/libpod-<id>.scope/container`, for both containers | Yes: they share the slice with the shell |

The plain placement (the first two rows) was run once inside the scope on each runtime (`n=1`); outside a scope the same paths were read in the four stack runs of measurements 2 and 3 (two per runtime). The slice variant ran twice (`MemoryMax=10G` for placement, `MemoryMax=300M` for the overrun), so its placement is `n=2` and its overrun `n=1`; the other rows `n=1` each. What this says:

- Under Docker the containers sit under the daemon whatever the shell's scope is, and a compose `cgroup_parent` can only name a slice of the system manager (`xxx.slice`), which the user cannot create or limit without root.
- Under Podman through `podman.socket` the containers are not under the caller's scope either, because the socket's service creates them; they sit under the user's instance (`user@1000.service`), so `systemd-oomd`'s `user@1000.service` rules cover them. With `cgroup_parent: <slice>` in a compose override, they are placed under a user slice the agent also runs in, and the slice's `MemoryMax`, `CPUQuota` and `MemorySwapMax` bind the agent and its stack together (the slice is set with `systemctl --user set-property`). `docker compose` accepts the key, and a service name is all the override needs.
- With the slice at `MemoryMax=10G` the stack ran and answered `204`; the slice's `memory.peak` read 463400960 bytes (441.9 MiB) with the shell and both containers.

**What happens when the stack exceeds the limit.** Not measured at `MemoryMax=10G`: the stack's peak is 0.41 GiB, and reaching 10 GiB means allocating that much on a host with 5.4 GB of its 7.9 GB swap already used, which risks the user's slice (and Herdr) through `systemd-oomd`. On 2026-11-11 the maintainer accepted the scaled run below as the evidence of measurement 4; the 10G run is follow-up 6 of the ADR. The same test, scaled down to what the stack really uses, was run with the slice at `MemoryMax=300M` and `MemorySwapMax=0` (the slice, shell and stack together, peaked at 441.9 MiB with the limit at 10G; the stack alone at 411 to 416 MiB, measurement 3): the stack started, `/_health` answered 204, and the slice's `memory.events` ended at `max 1514`, `oom 17`, `oom_kill 8`, `oom_group_kill 0`. Both containers reported `OOMKilled=true` with exit code 0 and status `running`: the kernel killed processes of the stack (8 kills), not the containers' main processes. `user@1000.service`'s own `memory.events` carried the same counters (events of a child are counted in its parent), the other terminals of the host were still alive afterwards (`hc ls`: t1, t17, t1z, t11q) and `systemd-oomd` did not act. Only one run (`n=1`) of this overrun.

### 5. What breaks or needs a change

Checked on the stack above and on a small scratch image (`alpine`) for what the stack does not exercise; each line is `n=1` except `depends_on`, published ports and named volumes, which the four stack runs exercised (`n=2` per runtime). The issue asks for at least two runs of each measurement: the `n=1` probes (build cache, SELinux, rootless networking) were not repeated, and the record does not claim more. On 2026-11-11 the maintainer accepted them at `n=1` and waived the two-run floor for them.
