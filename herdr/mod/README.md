# The factory mod for the Herdr desktop app

The mod of the epic "the maintainer runs the factory from a Herdr mod". The approved designs are in [`design/`](design/README.md); this folder holds what is built from them.

## Types

The mod is JavaScript with JSDoc types; it has no build step. [`tsconfig.json`](tsconfig.json) checks every `.js` and `.mjs` file of the mod under `strict` (`allowJs`, `checkJs`, `noEmit`), and `npm run typecheck` runs it:

```bash
npx tsc -p herdr/mod/tsconfig.json
```

[`types/`](types/) holds declarations only, outside `factory/`, so `install.sh` does not copy them. [`types/herdr.d.ts`](types/herdr.d.ts) and [`types/gpui.d.ts`](types/gpui.d.ts) declare the members of `herdr`, `gpui-kit` and `gpui-base` that the mod uses, taken from the type files the Herdr app writes in its configuration folder, which neither the repository nor CI has: a member the mod starts to use is added there. [`types/views.d.ts`](types/views.d.ts) has the types that several files of the mod share, `main.js` and the views most of them.

## The agent cats

A mod draws an image from a file under the app's configuration folder (`image("mods/<name>/…svg")`), so every cat the panel shows exists as a file. The source of all of them is [`design/cats.json`](design/cats.json) (the figures, the states, the crops and the badges) with the colours of [`design/tokens.json`](design/tokens.json).

```bash
node herdr/mod/build-cats.mjs              # writes herdr/mod/factory/cats/
node herdr/mod/build-cats.mjs --out <dir>  # writes them to <dir>
```

It reads only those two files, uses Node built-ins only and writes `<role>-<state>-<crop>-<theme>.svg`: 6 roles (`planner`, `master`, `worker`, `reviewer`, `verifier`, `scribe`), 5 states (`working`, `needs`, `idle`, `held`, `red`), 2 crops (`full`, `head`) and 2 themes (`dark`, `light`), 120 files, each with `viewBox="0 0 100 100"`. The same input gives the same bytes. `herdr/mod/factory/cats/` is in `.gitignore`: the files are generated, never committed.

Each file draws, in the order of the source: the silhouette (the role's body, stroked with the state's outline), the collar, the bell, the object's fill, the ink, then the eyes and the marks of the state. The `head` crop adds the role's round badge. The colours of the outline, the bell and the pause mark are the theme's tokens, so a file exists once per theme; the body, the ink and the collar are the role's own (the reviewer's ink and collar are `#e8f0ff`, the others' `#0b0c10`).

The glow of "needs you" is not in the files: the panel draws it.

`catFile(role, state, size, theme)` in [`factory/lib/cat.js`](factory/lib/cat.js) gives the name of the file to draw: the `head` crop under 32 px, the `full` crop from 32 px, and `undefined` for a name that has no role.

## The model

Every screen of the mod shows the same facts, so they are read once, by plain functions in [`factory/lib/`](factory/lib/) that import only each other and that vitest runs (`test/herdr-mod-model.test.ts`, with the recordings in `test/fixtures/herdr-mod/`). No function reads the clock, a file or the network: the time, the texts and the fetched JSON are arguments, and the calls that fetch them are the mod's own.

| Module       | Reads                                                                                                                                                                                                                                                | From                                                                                                                                                               |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `slots.js`   | the heavy slots, the leases, the queue, the orphans, `paused` and the maintainer's hold                                                                                                                                                              | the text of `herdr/factory-slot.sh status` (`status.txt`, `status-paused.txt`); the script prints no queue line today, and a `queue` line is read when it does     |
| `machine.js` | the 1-minute load, the memory in use (`MemTotal` minus `MemAvailable`), a CPU temperature; saturated when the load is above the core count                                                                                                           | the texts of `/proc/loadavg`, `/proc/meminfo` and each `hwmon` `name` with its `temp1_input`, and the core count (`herdr/mod/findings.md`, question 3)             |
| `gates.js`   | an issue's rounds, the six marks of its track (passed, running, needs you, held, red, not reached, omitted by lane), its lane and calibration                                                                                                        | the issue's comments as `gh api repos/<repo>/issues/<n>/comments` returns them: only the maintainer's login counts, as in `factory-tools metrics` (`--maintainer`) |
| `issues.js`  | a milestone's issues as rows: the track, the lane, the age of the wait and what blocks a blocked issue                                                                                                                                               | the milestone's issues as REST returns them and each one's comments; a `## Depends on` item that is an open issue of the milestone blocks it                       |
| `agents.js`  | each agent's name, role, status and space                                                                                                                                                                                                            | the rows of Herdr's `terminals()`, never `agents()` (findings, question 4)                                                                                         |
| `state.js`   | all of it, with an age per source and a `stale` mark on a source whose last read failed (it keeps its last value)                                                                                                                                    | what the other modules read, as one `fetched` object                                                                                                               |
| `reads.js`   | the time limits of the reads: a step that does not answer ends as an error of its own source, and a read that never ends does not keep the next one from starting; and when the epic of each space is read again, once an hour at most (`readEpics`) | the adapters of `adapters.js` and a `sleep` (`cx.sleep`); it runs no command and imports nothing from `herdr`                                                      |
| `spaces.js`  | the lines of the banner of the spaces: a pair's milestone that is closed or missing, and an epic of a space's first pair that is not an open epic ("Configure" below)                                                                                | the milestones and the epics as REST returns them, and the spaces of the layout (`test/herdr-mod-panel.test.ts`)                                                   |

The gate comments are those of `herdr/master.md`: `**Gate 1 …**` with a `lane: <lane>` line (and `(calibration: full)`), `**Gate 2, round K (master)** · pass …`, `**Gate 2, round K (master)** · red: …`, `**Gate 2, round K (master)** · sent back (not a round)`, `**Gate 3, round K (reviewer-N)** · K Blocking …` (or a summary that starts with `red`) and `**Gate 4, round K …** · M mismatches`. A comment with a Blocking above 0, a mismatch above 0, `not ready`, or a gate 2 or 3 summary that starts with `red`, marks its gate red, and a `sent back` one marks it running. A later comment of gate K resets the marks of the gates after K until their new rounds report, with G3 and G4 as one pair; `express` omits G3 and G4. G5 needs the maintainer once the gates before it passed, G5 is passed only by a `Progress updated … pull request #N opened` comment posted after the last gate comment, and a closed issue has every gate passed. The `held` mark is to be read from the `held |` comment of "The lines" below; the model does not read it yet, so no issue is held.

A role comes from a terminal's `name` (`worker-<N>`, `reviewer-<N>`, `reviewer-<N>-r<K>`, `verifier-<N>`, `verifier-<N>-r<K>`, each also as `worker-<tag><N>` for an issue of a space's tagged pair, which `parseAgents` gives as the agent's `tag`; `scribe`) or, with no name, from `--agent master` or `--agent planner` in `foreground.argv`. Its status is the terminal's `status`, and `blocked` means it needs the maintainer. Its space is that of its root terminal (the one with no `parent`), from that root's `herdr.space` label. The state carries no context size and no model: no field of `agents()` or `terminals()` gives a context size, and the model is only an argument of a command. The issue detail reads it where it is, with `modelOf` of `agents.js`: the argument after `--model` in a terminal's `foreground.argv`, `--` for a terminal that was started with none (the master's).

## The panel

[`factory/`](factory/) is the mod: a panel docked on the right of the window, or the left with `install.sh --side left` (`mod.json`: `place: right`, 380 px, `focusable`) that shows the state of the factory and, in "Needs you", sends the maintainer's sign-offs and answers to the masters. No command it runs for a read writes, and the mod writes no file: its settings go through `setShared`, its panel through `layout.hide` and `layout.show`, its Board through `tab.new`, `pane.rename` and `tab.close` ("Customize" below). It sends the lines of "Needs you" below and the correction form's `log #N | …` ("Log a correction" below), to the master of an issue's space and after the maintainer's click and a 10 s undo, and `retry #N` once for a retry the maintainer armed; the buttons of "The buttons" below act on the machine; it reads no token and stores none (`gh` finds its own login). `main.js` puts the reads of [`adapters.js`](factory/adapters.js) through the model above and the sections of [`factory/lib/panel.js`](factory/lib/panel.js) into one description, which one file of [`factory/views/`](factory/views/) per section draws: `header.js`, `strip.js`, `banners.js`, `machine.js`, `slots.js`, `leases.js`, `needs.js`, `milestones.js` (with `legend.js`), `stacks.js` and `orphans.js`, `detail.js` for the overlay of an issue, `board.js` for the Board tab and `customize.js` for Customize (below); the settings they read are those of [`factory/lib/settings.js`](factory/lib/settings.js).

### A low quota

GitHub's REST quota is 5000 calls an hour for the account, shared by every tool and agent on the host, and the panel reads on its own, as each Board tab and issue overlay does. Each read of an endpoint sends its `Etag` back as `If-None-Match`, and a `304` does not count against the quota; the adapters keep the `Etag` and the body of each endpoint's last `200` in memory only (nothing is written, and no token is read: ADR-0004, Decision 7). An issue's comments are read again only when its `updated_at` in the list changed, when none were read yet, or when the last read of them is 10 minutes old. The adapters also keep the last `X-Ratelimit-Remaining` and `X-Ratelimit-Reset` any reply gave (`lib/quota.js`): below 500 remaining the slow read happens at most once every 5 minutes and the header says `sync <age> · quota <remaining> · slow <time to reset>`; at 0 remaining, or on a 403 or 429 with `X-Ratelimit-Remaining: 0`, GitHub is not read until the reset (but for `rate_limit`, below, which costs no call) and the header says `sync <age> · quota 0 · paused <time to reset>` (`GH STALE <age>` keeps its place, with the same text after it, when GitHub is stale). Once the reset time has passed the pace is back to every 60 s. The slow read also waits while `window()?.visible` is `false`, where the platform reports the window hidden (on Wayland only for the `suspended` state of xdg-shell, so there it saves nothing). The files read locally are not paced. `Panel.png` has no element for the quota: it is plain muted text in the sync label.

GitHub also has a secondary limit, per minute, on the same account, and it refuses with calls still remaining: a `429`, or a `403` with `Retry-After` or whose body's `message` names a secondary rate limit, in each case with `X-Ratelimit-Remaining` not `0` (`secondaryOf` of `lib/quota.js`). It pauses every `gh` call of the adapters: for the seconds of `Retry-After`, or without it for 60 s, doubled on each further secondary reply in a row, at most 15 minutes; a `200` or a `304` ends the pause, unless its call was already running when a secondary reply arrived. While it runs no `gh` is run, each read fails with `secondary rate limit: paused until <HH:MM>` (UTC), so GitHub goes stale, and the sync label adds `· secondary · paused <time left>`. The pause is kept in memory only, one for each copy of the mod, as the `Etag`s are.

The masters and the agents spend the account's GraphQL points, which the panel does not. With the slow read, at most once every 5 minutes, and never while a secondary limit pauses the reads or the window is hidden, the mod runs `gh api rate_limit --include`, which does not count against the REST quota; while fewer than 500 GraphQL points remain before their reset, the sync label adds `· graphql <remaining> · reset <time to reset>`. The panel makes no GraphQL call, the REPORTS pane included: the pane reads the issue and its comments with `gh api` GETs (`lib/reports.js`).

### The issue detail

The id of an issue row in Milestones (and `herdr-app do factory.detail:<number>`) opens an overlay of the same mod, a dialog 760 px wide, with `detail` in its props (`main.js` draws [`views/detail.js`](factory/views/detail.js) when it has it; what it shows is computed by [`factory/lib/detail.js`](factory/lib/detail.js) and run by `test/herdr-mod-detail.test.ts`). It reads, and sends one thing: the answer of "Decision for you" (below) to the space's master, after the 10 s countdown; closing the overlay cancels the countdown, and nothing is sent. Nothing else:

- The header: the space's badge, the lane tag, the repository and number, the branch, the stack (`stack up: <name>` when `docker compose ls` lists a stack that ends with the issue's number, else `no stack up`: the design's "no stack needed" would need a source for what the issue needs, and none is given), the lines added and removed, and the title. The branch and the lines are read from the worktree named in the issue's `### Progress` or `## Progress` (`git rev-parse --abbrev-ref HEAD` and `git diff --numstat` against the merge base with `origin/main`, nothing that writes; a file that is not tracked yet is not counted).
- "Gates by round": one row per round, six cells G1 to G6. A cell holds the first line of the gate comment of that round, after `Gate N, round K (agent)`; a gate the lane omits is dashed in every row. A gate with no comment yet shows what its mark says (`running`, `needs you`, `waits`), and in the earlier rounds `--`.
- "Agents on this issue": the issue's agents (`worker-<N>`, `reviewer-<N>`, `verifier-<N>` and their reread names) and the space's master, each with its cat, model, state and tokens: input plus output summed from the `tokens |` lines of the issue's comments (`herdr/master.md`, "The tokens record"; the maintainer's login only, the issue's number only, one total for each role). An agent that has ended has no terminal any more: its row is made from its tokens line, state `done`. The design's Context column is left out, and so is the line under it that depends on it: no field of `terminals()` gives a context size (`findings.md`, question 4).
- "Packet": the worktree, the draft, the decisions file (`<packet>/r<K>/decisions.md`, K the latest round) and the commit message (`<packet>/commit-message.txt`), from the code spans after `worktree`, `packet directory`, `draft` and `branch` in the `### Progress` or `## Progress` section of the issue (`herdr/master.md`, "The review packet"). A path opens its file in a pane running `less`; an agent's name opens a pane running `watch -n 2 hc read <terminal> --lines 40`, so the keys go to `watch` and never to the worker. Each closes the overlay.

- "Decision for you", when the master has an open `**Decision needed**` comment on the issue: the question, one option per list item (A, B, …), a note and "Send to <space> · master". It sends `answer #N: <option>[ — <note>]` through the 10 s countdown, as "Needs you" does. The comment is open until a later comment of the maintainer's login starts with `Maintainer's decision, relayed by the master` (the form the master posts the answer in).

"Log a correction" in its header opens the correction form with the issue filled in ("Log a correction" below).

### Needs you

[`factory/views/needs.js`](factory/views/needs.js) is the first section of the panel, after the banners, and has no fold: it is there while something waits and gone when nothing does. What it shows is computed by [`factory/lib/needs.js`](factory/lib/needs.js) and [`factory/lib/time.js`](factory/lib/time.js) and run by `test/herdr-mod-needs.test.ts`. One card for each wait, oldest first, each with its age and the cat of the agent that waits:

- **A master that is blocked**: "Go to master" focuses its pane (`pane.focus`). `terminals()` gives no time for a status, so its age is counted from when the panel first saw it blocked, and it restarts with the panel. `blocked` is read as the model reads it ("needs the maintainer"), with the caveat of "What each section reads": `hc get` reported `blocked` for a worker that was only running a long shell command, so the card can be a false alarm, and the text says "Waiting for your reply in its pane."
- **A sign-off**: an issue whose G5 needs you and whose lane is not `express`. The review and verification lines are what the last Gate 3 and Gate 4 comments say after `Gate N, round K (agent)`, the lane is the `lane:` line of the Gate 1 comment with the lines under it as the reason, and the commit's subject is the first line of `<packet>/commit-message.txt`. "Open diff" opens `git diff` against the merge base with `origin/main` of the worktree named in the issue's `### Progress` or `## Progress`, in a pane running `less`; "Reports" opens the issue and its comments, read with `gh api`, in one. A sign-off whose issue's Progress names no worktree says `Open diff needs the worktree in the issue's Progress.` (`NO_WORKTREE_NOTE`) instead of the locked note. The time form and the sign-off stay locked, in every lane, until "Open diff" was clicked for that issue in this session (kept in memory: a reload of the mod locks it again).
- **A decision**: an issue with an open `**Decision needed**` comment. "Answer through the master" opens the issue detail, whose "Decision for you" block takes the option and the note.
- **An open pull request with no time note**: a pull request that names an issue of the milestone (`Closes #N`, `Fixes #N`, `Resolves #N`, `Refs #N`, the first one of the body, in any case) and has no `time:` note from the maintainer, in a comment of its conversation or in a review; the card says "No time note from you on this pull request yet." ("Log time" of `Panel.png`). With no maintainer login there is no such card: a pull request with a note cannot be told from one without. The panel reads the open pull requests of the repository of each pair of a space, with their comments and reviews, at the pace of the slow read: every 60 s, every 5 minutes while fewer than 500 calls of GitHub's hourly quota remain, and not at all while it is 0 or the window is hidden ("A low quota"). The issue a pull request names is read from its body once per read of GitHub (`pullIssue` of `lib/panel.js`), and the read keeps its number and not the body; a pull request of a bot (`user.type` `Bot`, or a login that ends in `[bot]`) is left out, and its comments and reviews are not read. Each `gh api` call is a conditional request (`--include`, and `--header If-None-Match: <etag>` once the endpoint has answered `200`), and a `304` gives the body kept in memory; the comments and reviews of a pull request are read again only when its `updated_at` changed or 10 minutes passed (a failed read of them is no pull requests, and never fails the read of the milestone). "Log time" opens the form of `TimeLog.png` in the card: Noted, Diff or Reports (Noted leaves the reading out, "Only if not noted yet; a later note keeps it."), the minutes, the hands-on check (None, Stack, Test, only in `full`) with a timer that adds the whole minutes it ran (at least one) to the field when it stops, a remark, and the line under "Posted on the PR". "Post time note" sends `time #N: time: <minutes>m …` to the master, which posts the line as the review comment; a pull request that already has a note gets no card, and the master posts nothing for one that has it ("Lines from the mod").
- **The green `express` issues**: one card for each space, so a click sends exactly one message, to that space's master. "Read the N diffs" opens the diff of each one not read; "Sign off K express" sends `approved, sign off #N #M` for the K whose diff was read and that are `express`, and no time line.

The time form of a sign-off is `TimeForm`: what was read first (Diff or Reports), the minutes (counted since the diff was opened, kept up to date until edited), the hands-on check (None, Stack, Test, and only in `full`), a remark (its parentheses and line breaks are dropped) and the lines it will send, `approved, sign off #N` and `time: <minutes>m diff|report[, <minutes>m stack|test][ (<remark>)]`. The "Start timer" of the design is in the form of an open pull request (below), not in this one.

A click on the sign-off, or on "Send to <space> · master", starts a 10 s countdown with an "Undo"; undone, nothing is sent, and at 10 s exactly one `hc send <master's terminal> <text>` is made (`lib/needs.js`, `createOutbox`; the two lines of a sign-off are one message). The master is the terminal with `--agent master` whose root has that space's label; with none, the button is off. `hc send` refuses a master that reported `blocked` (exit 9) and the panel does not force it: the line is not sent and the panel says why. With `fixture` in the props the countdown runs and nothing is sent. No call of this section writes to a worker's pane or to GitHub.

**Log a correction** is a form of its own, an overlay of this mod opened with `log` in its props (`main.js` draws `logForm` of [`views/detail.js`](factory/views/detail.js) when it has it; what it says is computed by [`factory/lib/log.js`](factory/lib/log.js) and run by `test/herdr-mod-forms.test.ts`). It opens from "log a correction" in the footer of the panel (`footer` of [`views/legend.js`](factory/views/legend.js)), from "Log a correction" in the issue detail (with the issue filled in) and from `herdr-app do factory.log:<number>`. It holds the issue (`#N`, or `owner/repo#N` for an issue of another repository of a space), what was wrong, one of the six categories (`lint`, `test`, `skill`, `standard`, `issue`, `docs`; none is chosen until the maintainer picks one) and shows the line the master will post, `factory-log | <date> | #N | <what> | <category> | -`. "Send to <space> · master" starts the same 10 s countdown and sends `log #N | <what> | <category>` (`log owner/repo#N | …`) to the master of the space whose milestone holds the issue (else the space it was opened from); a `|` in the text is sent as `\|` and its line breaks as spaces. Closing the window cancels the countdown. The design's `repo#n` form is accepted as `owner/repo#N`, the form of `herdr/master.md`; `herdr-app do factory.log:<number>` and `factory.detail:<number>` still take a number of a space's repository. The mod posts nothing on GitHub.

A desktop notification (`notify`, level `warning`, its action the command `factory.reveal:needs` of the docked panel, which scrolls it to "Needs you"; `mod.open` would open a new copy of the mod with no props) is posted when a card appears that the last look did not have; the first look after the panel starts posts none. In a fixture none is posted. Customize switches each alert ("Alerts" below).

### Customize

"Customize" in the header of the panel (the button with three bars) and in the Board's summary, and `herdr-app do factory.customize`, open an overlay of this mod, a dialog 420 px wide, with `customize` in its props (`main.js` draws [`views/customize.js`](factory/views/customize.js) when it has it; what it changes is [`factory/lib/settings.js`](factory/lib/settings.js), run by `test/herdr-mod-settings.test.ts` through stubs). The view only draws. Its groups, from `design/screens/Customize.png` (the Theme group is not built: the mod follows the Herdr app's theme, "Configure" below):

- **Where it shows.** "Side panel" runs `layout.hide {id: "factory"}` when it is switched off and `layout.show {id: "factory"}` when it is switched on. Herdr keeps a hidden or shown node as a click in `layouts/.state/factory.json`, never in `layouts/factory.json`, so `install.sh` still finds its own hash. With the panel off, Customize opens from the Board's summary or from `herdr-app do factory.customize`, and `herdr-app do layout.show --id factory` brings the panel back. "Board tab" switched on opens one Board tab when none is open (`tab.new`, as "Open board" does), switched off closes every Board tab this mod opened and hides "Open board" in Milestones (the `B` key and `factory.board` then open nothing). `PaneInfo` of `panes()` has no `props`, so the mod names the pane of each Board tab it opens: `tab.new`, then `pane.rename {pane, name: "factory-board"}` of the new pane, found in `panes()` (the focused pane of this mod with no name; with none, nothing is renamed), and the tabs it closes are those of the panes with `mod` `factory` and that name (`panes()`, then `tab.close {id, confirmed: true}`); a Board tab opened before this change, with no such name, is not closed. "Panel side" shows the side `install.sh` wrote (the `side` prop) and the line "Set with `herdr/mod/install.sh --side left` (README, Install)": a click on its two buttons changes nothing. The mod never runs `layout.set` or `layout.clone` and never writes a layout file.
- **Panel sections**: move up, move down, show or hide, and how many are shown (`5/7 shown`). "Needs you" cannot be hidden while something waits: it collapses to its heading and a count. A hidden section that turns red (the machine saturated, a red gate, an orphan, stacks that cannot be read) turns the panel's header red: the docked panel has no tab of its own.
- **Alerts**: "Something needs you" (the notification above), "Machine saturated" (one when the 1-minute load stays above the core count for a minute, and again only after it fell to the core count), "Held or red gate" (one for each `held |` line or red gate that the last look did not have) and "Sound" (`playSound` once with each notification that is posted, never on its own). An alert that is off posts nothing. Only the docked panel posts them.
- **Keys**: what [the keys](#the-keys) below say, with the key that acts.
- **Restore defaults** sets the settings to `null`, which reads back as the defaults.

The settings are one value, `shared("factory.settings")`, written with `setShared` (Herdr's `shared.json`, saved by the app): the panel, the Board tab and the Customize overlay are copies of the mod with different props, and `localStorage` is kept per set of props (`findings.md`, question 12), so only `shared` gives the three copies one set of settings, kept when `install.sh` is run again with other spaces. The fold of a section stays in `localStorage`. A stored value reads back field by field: a missing, unknown or mistyped field takes its default. With `fixture` in the props Customize changes what it shows and keeps the change in memory only: no `setShared`, no `layout.*`, no `tab.*` and no `playSound`. `layout.hide`, `layout.show` and the way `layouts/.state/` keeps them, and the `pane.rename` of a new Board tab's pane (it names the new pane, which `tab.new` focuses and `panes()` gives as focused) with the closing of the tabs it named, were not run on Herdr 0.1.17 (they would change the maintainer's window).

#### The keys

The panel has the keyboard when a click or `pane.go` gave it (`mod.json` has `"focusable": true`; the panel handles the keys with `track_focus` and `on_key_down`, only while it has the keyboard). The footer of the panel lists them, and the text of `[L]` in it is the link that opens the correction form.

| Key | Does                                                                                                                        | Command         |
| --- | --------------------------------------------------------------------------------------------------------------------------- | --------------- |
| N   | scrolls to the next card of Needs you, the first after the last                                                             | `factory.next`  |
| S   | signs off the oldest sign-off card, as its button does (the diff lock and the 10 s undo apply; a locked card sends nothing) | none            |
| P   | pauses or resumes new workers, as the button                                                                                | none            |
| R   | reserves or releases a heavy slot, as the button                                                                            | none            |
| L   | opens the correction form                                                                                                   | `factory.log`   |
| B   | opens the Board tab                                                                                                         | `factory.board` |

N, L and B are commands too. Rebind one by adding a `mod:factory` section to your own `keys.json`, for example `{ "mod:factory": { "alt-n": "factory.next" } }`: the panel reads `keys()`, a binding of the command replaces its default letter (the letter then does nothing) and Customize shows the key that acts. S, P and R are keys of the focused panel only and no command, because a `factory.<command>` can be run by any program with `herdr-app do`, and a sign-off, a pause or a hold must come from the maintainer's hand, as a click does; they cannot be rebound. Nobody merges or writes `keys.json`: the mod ships none and `install.sh` never touches it (Herdr's reference: any edit of `keys.json`, "even whitespace", keeps the whole file as the person's and stops its upgrades). Whether `keys()` lists a `mod:factory` binding under that section and the command's name was not run (it needs the maintainer's `keys.json`).

### The Board

"Open board" in the heading of Milestones (and `herdr-app do tab.new --name Board --mod factory --props '{"board":true, …}'`, with the block's other props) opens this mod as a tab of its own with `board` in its props (`main.js` draws [`views/board.js`](factory/views/board.js) when it has it; what it shows is computed by [`factory/lib/board.js`](factory/lib/board.js) and run by `test/herdr-mod-board.test.ts`). It reads and sends nothing: a card opens the issue detail and does nothing else, and there is no dragging; "Customize" in its summary opens the overlay above. With no maintainer login in the layout its note starts with `No maintainer login: the gates are not read` ("Configure").

- The summary: load (the 1-minute load over the core count, magenta above 75 % of it and red above it), heavy slots, workers, queue, orphans and the factory's share.
- The filters: one button per space, `<SPACE> · <closed>/<all>` (the pull requests merged, as in Milestones), and one per lane (`EXPRESS`, `NORMAL`, `FULL`). They combine and the counts of the columns follow them; the summary does not. The design's "ctx 201k" is left out: no field of `terminals()` gives a context size (`findings.md`, question 4).
- Seven columns: Ready, G2 · Worker, G3 · Review, G4 · Verify, G5 · Needs you (the maintainer's, dashed magenta), G6 · CI and Merged today. An issue is in one column, the one its last gate comment puts it in: no gate comment is Ready; a gate sent back, and a red gate 2, is G2; a red gate 3 or 4 stays in its own column marked red; a gate that passed sends it to the next gate its lane does not omit and that has not passed (G3 and G4 run together, so an issue is in G3 until its review passed); `Progress updated … pull request #N opened` moves it to G6. A new round of gate 2 sends the issue back to G2 while that round runs, and to G3 once it passes, whatever gates 3 and 4 said before. A closed issue is in Merged today when it was closed today (UTC). The design draws an issue twice while G3 and G4 run together; the Board does not (it is in exactly one column).
- Ready is the Status Ready. The Status of the project is a GraphQL read (or a REST read that needs the project's number), and the panel runs `gh api` GET calls only: an open issue with no gate comment is in Ready when it has the label `ready`, which `issue-ready` sets with the Status, and it is Todo, and not on the Board, without it.
- A card: the space's badge, `#<issue>`, the lane tag, the round, a sentence (the title; `Blocked by #N` for a blocked one; `Waits for your sign-off` in G5; the first line of a red gate's comment), the cat and name of the issue's agent for that column (the worker in G2, the reviewer in G3, the verifier in G4, the space's master in G5 and G6; any other agent of the issue, none in Ready) and how long since the last gate comment (`waiting 4 h` for a card that needs you, `held 6 min` for a held one). A card that needs you is magenta, a held one has the acid stripe (the model reads no held issue yet, see "The model"), a red one is red.
- The factory's share is the issues of the milestones whose `front` is `Foundations` in `.github/project-fields.json` (the `frontByRepository` of a repository first) over the issues of every milestone of the same `releaseLine`, in the repositories of every pair of the spaces; a milestone's issues are its `open_issues` and `closed_issues` of `gh api repos/<repo>/milestones?state=all`. The line is that of the first space's milestone found in the file; with none, the share is `—`.

The Board's tab reads on the same timers as the panel (5 s and 60 s); the milestones and the file are read with the 60 s read of GitHub. The comments of an issue closed today are read too, for the lane of its card. At the window's width the Board scrolls sideways below 1330 px, as the design does.

### Install

```bash
herdr/mod/install.sh --maintainer <your GitHub login> --spaces <spaces.json> [--side left|right]
```

It builds the cats and copies the mod to `${HERDR_APP_DIR:-$HOME/.config/herdr-app}/mods/factory/` and the layout to `layouts/factory.json` (Herdr's `main` with the panel on the right, or the left with `--side left`: the `factory` block is the last child of `work-body`, or the first, and the `side` prop says which; `layout.switch {name: "factory"}`, or `ctrl-shift-l`, shows it). It never overwrites a file it did not write: it records the hash of each file it writes in `factory-mod-install.json` of that folder, and when a file it would write exists with another hash (one it did not write, or one it wrote and you then edited) it writes nothing, names the file and exits 1. Run again, it replaces what it wrote.

The maintainer login comes from the first of: `--maintainer <login>`; `$FACTORY_MAINTAINER`; the `maintainer` of the installed `layouts/factory.json`, only when that file is as this installer wrote it (its hash is the one in `factory-mod-install.json`) and the value is a login, which `install.sh` says on stderr (`install.sh: maintainer <login>, kept from the installed layout`), so a reinstall that changes only the spaces keeps who the maintainer is. With none of them it writes nothing, prints `install.sh: no maintainer: give --maintainer <login> or set FACTORY_MAINTAINER` and exits 2. A `--maintainer` or `$FACTORY_MAINTAINER` that is not a GitHub login (`^[A-Za-z0-9][A-Za-z0-9-]{0,38}$`, `--maintainer ""` included) writes nothing and exits 2 as well. A layout you edited is never read for the login.

An install made before the `dockerHost` prop existed runs `docker` with no `-H` until `install.sh` is run again. `--fixture <folder>` (repeatable) makes it read recordings, as below. The mod follows the Herdr app's theme and has no theme option: change the light or dark mode and the colours with the app's own theme menu or `app.theme`. Herdr loads the `fonts/` folder at start and at the next look change, not when the mod reloads: a first install shows the interface font until then.

The panel reads each pair's milestone and open pull requests in that pair's repository (`readGithub` and `readPulls`, one more of each `gh api` GET per pair) and shows the pairs' issues in the space's one Milestones block. An issue of another repository is named `owner/repo#N` (`bogd3v/micelio-cms#531`) in its row, its cards, the Board and the issue detail, and its agents are `worker-<tag><N>`, `reviewer-<tag><N>[-r<K>]` and `verifier-<tag><N>[-r<K>]` (`worker-c531`); `worker-<N>` stays on issue N of the space's repository. - `<space>: milestone <n> of <repo> is closed`, for any pair;
- `<space>: <repo> has no milestone <n>`, for any pair whose milestone is not among its repository's (the first 100, the one page the read asks for);
- `<space>: #<epic> of <repo> is not an open epic`, for the epic of a space's first pair when it is a pull request, a closed issue, or an issue whose title does not start `Epic:` and that lacks the label `épica` (the title and the label of the epic template).

The epic of a tagged pair is not checked: it is only left out of that pair's rows, and may be the space's epic number in a repository that has no such issue. The banner only warns: no entry is left out, reordered or changed, and `install.sh` checks nothing of this. A read that failed gives no line of its own (a number that does not exist as an issue is such a read, a 404), and a later failure keeps what the last good read said. With no line there is no banner.

The mod follows the app's theme: the light or dark mode (`settings().dark`) and the neutral colours (`bg` from `canvas`, `surface`, `surface2` from `raised`, `line` from `border`, `fg` from `foreground`, `muted`), read from `theme()` at each render, so a change shows within 5 s. The colours of meaning (running, needs you, red, held) stay the design's, for the app's mode, and a colour the app's theme lacks keeps the design's. A `theme` that an earlier install left in `localStorage` or in the layout is ignored.

A section folds with a click on its heading; the fold is kept in the mod's `localStorage`. Whether it survives a restart of the app was not run (`findings.md`, question 12). The commands `factory.top`, `factory.next`, `factory.board`, `factory.customize` and `factory.reveal:<section>` (`herdr-app do factory.reveal:milestones`; `needs`, and `card-<n>` for the nth card of Needs you) scroll the panel (`factory.next`: to the next card of Needs you), `factory.board` and `factory.customize` open the Board tab and Customize, and `factory.detail:<number>` opens the overlay of an issue.

### The buttons

Four things the maintainer does when the machine saturates, each a click that [`factory/lib/actions.js`](factory/lib/actions.js) runs through Herdr's `exec` (`test/herdr-mod-actions.test.ts` runs them through a stub, never the live machine). With `fixture` in the props nothing runs at all: `createActions` and `createRetries` of `lib/actions.js` take `disabled`, which `main.js` sets from `fixture`, so no slot script command, no `docker`, no `kill` and no `retry` send is made whatever is clicked, and a click says "Fixture: nothing was run." (`test/fixtures/herdr-mod/actions/` holds the paused state, a held check, an unowned stack and an orphan for the shots).

- **"Pause new workers" / "Resume workers"** (under the alarms, with the paused line the design shows): `herdr/factory-slot.sh pause` and `resume`. The label follows the `paused` line of `status`, read every 5 s and again after a click.
- **"Reserve a slot" / "Release my slot"**: `herdr/factory-slot.sh hold --agent maintainer` and `release --agent maintainer`. A hold that exits 75 holds nothing and the panel says "no free slot". The label follows the `held` slot of `status`.
- **A held check in "Needs you"**: a card for the last `held | <date> | #N | <gate> | <reason>` line of an issue's comments, until a later comment of the same gate reports the rerun. It shows the reason and "Retry when load < 24" (three quarters of the core count, so 24 on the design's 32 threads and 6 on 8 cores), which arms it: when the 1-minute load falls under that number the mod sends `retry #N` to the issue's master (the line of "The lines" below), once, and the retry is no longer armed. "Armed · cancel" disarms it. An armed retry lives in the mod's memory: closing the panel drops it.
- **Stacks up and Orphans**: a stack with no live agent and no lease shows its age (the oldest container, `docker -H <dockerHost> ps -a --filter label=com.docker.compose.project=<project>`) and "Bring down <project>…", which after a confirmation that names the project runs `docker -H <dockerHost> compose -p <project> down -v` (every `docker` call goes through `dockerArgs`, ADR-0002). An orphan shows "Show process" (its command, working directory, cores and age, from `ps -o etimes=,pcpu=`) and "Terminate…", which after a confirmation that names the process ends its process group with `kill -TERM`. Both are offered only for what no live agent and no lease owns, and are checked again when the confirmation is answered. For processes, `factory-slot.sh status` decides: it leaves out every ancestor of a slot's wrapper (a waiting one included) and every process that descends from a live one (PID 1 aside) that carries `FACTORY_AGENT` or `HC_TERMINAL_ID`. The card shows the program and its working directory on one line, and "Show process" shows the command cut to 120 characters.

A failed `gh` makes GitHub stale: the banner gives its age, Milestones keeps its last rows dimmed, and the other sections go on. A failed or silent read of a local source makes it stale the same way: a stale machine dims Machine, a stale slots source dims Heavy slots, Worker leases and Orphans, and a stale agents source dims the cats of Milestones and the agent cards of Needs you, each with `as of <HH:MM> UTC · not live` (one note on Needs you), and the Board's note says `Not live since <HH:MM> UTC: <sources>`, the oldest last good read of the stale ones, joined with GitHub's note by `·`. A step that does not answer is cut at its limit by [`factory/lib/reads.js`](factory/lib/reads.js): 20 s for each step of the 5 s read (more than the 15 s of its longest `exec`), 45 s for each GitHub step of the 60 s read (more than `gh api`'s 30 s), and the sources whose step failed are the stale ones. A read that never ends (its task cancelled, its `finally` never run) holds the next one for 60 s (the 5 s read) or 10 min (the 60 s read), and its late result is dropped. A `hwmon` file that cannot be read is left out as if it were absent. The age of `sync` is made from the clock and each source's last good read at every redraw, so it grows while no read lands. The limit adds no command and no `exec` option (ADR-0004). The panel shows no context size (no field of `terminals()` gives one, `findings.md`, question 4), no memory per stack, and the age of a stack nobody owns is read from its containers (`docker compose ls` gives none). A `blocked` terminal is shown as an agent that may need you, as the model reads it ("needs the maintainer"), with a caveat: `hc get` reported `blocked` for a worker that was only running a long shell command, so a needs-you cat, mark or count can be a false alarm; the note says "is blocked: it may need you". The rows of Milestones are built at each redraw from the agents of the last 5 s read and the last 60 s read of GitHub, so an agent that starts, stops or blocks shows within 5 s.

### The lines

What the panel's buttons send (the sign-off and the answer, #304; the retry, #305; the time note and the correction, #306) and what the master posts for the panel to show; the rules are [`herdr/master.md`](../master.md), "Lines from the mod", with `G5.2`, `G5.5`, `M.8` and `C.1` of [`docs/factory.md`](../../docs/factory.md). The mod sends each line bare (`hc send`, no `HC_TERMINAL_ID`), only to the master of the issue's space. The lines of a click (the sign-off, the answer, the time note, the correction) wait the 10 s undo (ADR-0004); `retry #N` does not: the click only arms it, and the mod sends it once, with no undo, when the load falls under three quarters of the cores ("Armed · cancel" before that disarms it).

Each line the mod sends, and what the master does with it:

A line names its issue by its reference: `#N` for an issue of the space's repository, `owner/repo#N` for an issue of another repository of the space (`approved, sign off bogd3v/micelio-cms#531`, `retry bogd3v/micelio-cms#531`); a shared sign-off names each one (`approved, sign off #6 bogd3v/micelio-cms#6`). What the mod keeps per issue (the diffs opened, the forms, the commit subjects, the armed retries) is keyed by the number in the space's repository and by `owner/repo#N` in another, so two issues of the same number never share one.

- `approved, sign off #N`, followed or not by a line `time: <minutes>m diff|report[, <minutes>m stack|test][ (<remark>)]`: the master signs off (`G5.2`), then posts the `time:` line as the pull request's review comment (`G5.5`).
- `answer #N: <option>[ — <note>]`: it records the answer in `decisions.md` and on the issue, then passes it to the worker.
- `retry #N` (sent by the mod when an armed retry's load is reached, not at a click): it reruns the held check once through `herdr/factory-slot.sh run`; a second failure is red.
- `log #N | <what> | <category>`: it posts `factory-log | <date> | #N | <what> | <category> | -` on the issue.
- `time #N: <the time line>`: it posts the time line on the open pull request that has none.

The master posts on the issue, for the panel to read:

- `**Decision needed** · #N`, the question and one list item per option (`- A: …`), when a worker waits for the maintainer ("Decision for you" of `IssueDetail`).
- `held | <date> | #N | <gate> | <reason>` when a check failed only on timeouts while the load was above the core count (the held check of `PanelSaturated`); `owner/repo#N` is read too.
